# Amnezia Panel: управление пользователями и веб-кабинет

Дата: 2026-09-26
Статус: дизайн согласован, ожидает ревью spec
Ветка: `feat/panel`

## 1. Контекст

Сейчас у AmneziaVPN нет серверной части. Администратор управляет серверами из десктоп-клиента по SSH (root или sudo).

Модели «пользователь» в клиенте нет, есть только таблица клиентов. Её хранит каждый контейнер в своём файле `/opt/amnezia/<container>/clientsTable`. Запись таблицы — это `clientId` (публичный ключ WireGuard, UUID Xray или CN сертификата OpenVPN) и `clientName`. Логика находится в `client/core/controllers/selfhosted/usersController.cpp`.

Ограничения текущего решения:

- Нет сущности, которая объединяла бы конфиги одного человека на разных протоколах и серверах.
- Revoke необратим. Блокировки без удаления нет.
- Нет срока доступа и лимита конфигов.
- Трафик виден только для WireGuard и AWG (`wg show`) и только пока клиент открыт.
- Приватные ключи клиентов нигде не хранятся, поэтому повторно выдать уже созданный конфиг нельзя.
- Самообслуживания для конечных пользователей нет.

## 2. Цели

### А. Администрирование

- **А.1.** Администратор создаёт пользователя, а не конфиг. Конфиги любого поддерживаемого протокола создаются уже для пользователя. При создании пользователя генерируется ключ приглашения, по которому пользователь регистрируется в веб-кабинете.
- **А.2.** Существующий конфиг можно выдать повторно (скопировать или показать QR), не пересоздавая его.
- **А.3.** Серверы образуют один кластер. Каждому пользователю доступны все серверы панели, у которых включён флаг «доступен пользователям».
- **А.4.** Пользователя можно заблокировать и удалить:
  - Блокировка отключает все его конфиги, но не удаляет их.
  - Разблокировка возвращает конфиги в работу.
  - Удаление удаляет пользователя вместе со всеми его конфигами.
- **А.5.** У пользователя есть срок доступа (дата). Когда срок наступает, пользователь блокируется автоматически.
- **А.6.** У пользователя есть лимит конфигов. Сверх лимита конфиги не создаются.
- **А.7.** Трафик пользователя показывается в сумме по всем конфигам и отдельно по каждому серверу.

### Б. Веб-кабинет пользователя

- **Б.1.** Вход по логину и паролю.
- **Б.2.** Под формой входа есть кнопка «Ввести ключ для авторизации». После ввода ключа пользователь задаёт логин и пароль, пароль должен соответствовать политике безопасности. Ключ одноразовый: он действует, пока по нему не зарегистрировались.
- **Б.3.** Дашборд показывает:
  - доступные серверы;
  - сколько конфигов ещё можно создать.

  На дашборде можно:
  - создать конфиг на выбранном сервере;
  - удалить или заблокировать свои конфиги;
  - повторно выдать конфиг.
- **Б.4.** Страница аккаунта со сменой пароля.

### Не цели

- Биллинг и оплата.
- Лимиты по трафику.
- Несколько кластеров и групп серверов.
- 2FA.
- Вход конечного пользователя в Qt-клиент через панель: пользователь импортирует ключ `vpn://`.
- Замена существующего self-hosted режима Qt-клиента по SSH: он остаётся без изменений.

## 3. Ключевые решения

| Вопрос | Решение |
|---|---|
| Где живёт логика | Отдельный бэкенд «панель». Qt-клиент не подходит: он часто выключен, а автоблокировке и веб-кабинету нужен постоянно работающий процесс. |
| Интерфейс администратора | Веб-админка и админские экраны в Qt-клиенте поверх одного REST API. |
| Связь панели с VPN-серверами | SSH из панели. Агента на серверах нет. |
| Стек бэкенда | Python 3.12, FastAPI, SQLAlchemy 2 с Alembic, asyncssh, APScheduler. |
| Стек фронтенда | Одностраничное приложение на React, TypeScript и Vite поверх того же REST API. |
| Развёртывание | Отдельный VPS, docker compose: Caddy, backend, PostgreSQL. |
| Протоколы | Все протоколы и сервисы, которые можно выдавать пользователям. Внедряются поэтапно, см. §11. |
| Существующие серверы | Импортируются. Найденные клиенты становятся конфигами «без владельца». |
| Кластеры | Один неявный кластер: все серверы панели с `enabled_for_users`. |
| Размещение кода | Монорепо, каталог `panel/` рядом с `client/`. Скрипты из `client/server_scripts/` используются без копирования. |

### Главный принцип: желаемое состояние и сверка

Источник истины — БД панели. Блокировка, разблокировка, удаление и истечение срока только меняют строки в БД и ставят задачу `reconcile(server)`.

Задача `reconcile(server)` работает так:

1. Драйвер каждого протокола на сервере читает фактический набор клиентов.
2. Этот набор сравнивается с желаемым: активные конфиги сервера из БД.
3. Драйвер добавляет недостающих клиентов и убирает лишних.

Сверка идемпотентна. Повторный запуск после сбоя на середине безопасен.

Правило для «лишних» клиентов на сервере:

- клиент, которого нет в БД, импортируется как конфиг без владельца (`user_id = NULL`) и остаётся активным;
- удаляются только клиенты, которых панель сама пометила как удалённые или неактивные.

Благодаря этому клиенты, созданные вручную или старым Qt-клиентом, не пропадают.

Импорт нового сервера — это та же сверка в режиме «только записать найденное в БД».

## 5. Модель данных

Все отметки времени хранятся в UTC (`timestamptz`).

```
admins          id, login UNIQUE, password_hash, created_at

users           id, display_name, note,
                login UNIQUE NULL, password_hash NULL,     -- пусто до регистрации по ключу
                blocked_by NULL | 'admin' | 'expiry',
                expires_at NULL, max_configs INT NOT NULL,
                deleting_at NULL,                          -- удаление ждёт сверки
                created_at

invite_keys     id, user_id FK, key_hash UNIQUE, created_at, used_at NULL, revoked_at NULL

servers         id, name, host, ssh_port, ssh_user, ssh_secret_enc,
                host_key,                                  -- TOFU
                enabled_for_users BOOL,
                prepared_at NULL, imported_at NULL,
                last_ok_at NULL, last_error NULL

server_containers  server_id FK, container, params_json, refreshed_at
                   PK (server_id, container)

configs         id, user_id FK NULL,                       -- NULL = без владельца
                server_id FK, container, name,
                client_id,                                 -- ключ сверки: pubkey / UUID / CN / логин
                material_enc NULL,                         -- приватная часть; NULL у импортированных
                blocked_by NULL | 'user' | 'admin',
                deleted_at NULL,                           -- удаление ждёт сверки
                last_rx BIGINT, last_tx BIGINT, counter_session NULL,
                created_at
                UNIQUE (server_id, container, client_id)

traffic_daily   config_id FK, day DATE, rx BIGINT, tx BIGINT   PK (config_id, day)

sessions        id, subject ('admin'|'user'), subject_id, token_hash UNIQUE,
                created_at, last_used_at, expires_at, revoked_at NULL

jobs            id, kind, server_id NULL, payload_json, status, run_after,
                attempts, last_error, locked_at, created_at, finished_at

audit_log       id, actor ('admin:<id>'|'user:<id>'|'system'), action, target, details_json, ts
```

### Правила предметной области

- **Активность конфига.** Конфиг активен на сервере, когда выполнены все условия:
  - `configs.deleted_at IS NULL`;
  - `configs.blocked_by IS NULL`;
  - если у конфига есть владелец: у владельца `blocked_by IS NULL`, `deleting_at IS NULL` и срок не истёк.
- **Независимые блокировки.** Блокировка пользователя и блокировка конфига хранятся отдельно. Снятие блокировки с пользователя не разблокирует конфиги, которые он заблокировал сам.
- **Права на разблокировку.**
  - Пользователь может снять с конфига только блокировку `blocked_by = 'user'`.
  - Администратор может снять любую блокировку.
- **Лимит.**
  - Создание конфига разрешено, пока `count(configs WHERE user_id = ? AND deleted_at IS NULL) < max_configs`.
  - Заблокированные конфиги тоже учитываются.
  - Проверка и вставка идут в одной транзакции под `SELECT ... FOR UPDATE` по строке пользователя.
- **Срок.**
  - Администратор вводит дату. Эта дата — последний день доступа.
  - Доступ заканчивается в 00:00 следующего дня в часовом поясе `PANEL_TZ`, в БД хранится этот момент в UTC.
  - Когда срок наступает, ставится `blocked_by = 'expiry'`.
  - Если администратор продлевает срок, `'expiry'` снимается. Блокировку `'admin'` продление не снимает.
- **Вход при блокировке.** Заблокированный пользователь и пользователь с истёкшим сроком могут войти в кабинет и видят свой статус. Создавать и получать конфиги они не могут.
- **Ключ приглашения.**
  - Ключ — 128 случайных бит в base32 с группировкой по 4 символа.
  - Администратор видит ключ один раз. В БД хранится только SHA-256 ключа.
  - Перевыпуск ставит у старого ключа `revoked_at`.
  - Когда пользователь регистрируется по ключу, у ключа ставится `used_at`. Ключ с `used_at` или `revoked_at` не принимается.
- **Трафик.**
  - Дельта: `new − last`. Если счётчик уменьшился или сменилась сессия (`counter_session`), дельтой считается `new`.
  - Дельта прибавляется к `traffic_daily` за текущие сутки в `PANEL_TZ`.
  - Итоги по пользователю и серверу считаются агрегатами, отдельно не хранятся.
- **Удаление пользователя.**
  1. Ставится `users.deleting_at` и `configs.deleted_at` у всех его конфигов.
  2. Ставится задача сверки.
  3. После успешной сверки на всех затронутых серверах строки удаляются физически.
  4. Пока идёт удаление, вход запрещён.

## 6. Драйверы протоколов

### Интерфейс

```python
class Driver(Protocol):
    container: str
    async def prepare(self, srv: ServerCtx) -> PrepareReport          # разовая подготовка контейнера
    async def read_params(self, srv) -> dict                          # порт, ключи сервера, AWG-параметры...
    async def list_clients(self, srv) -> dict[str, ClientInfo]        # client_id -> данные для импорта
    async def create_material(self, srv, params) -> ClientMaterial    # генерирует ключи/UUID/сертификат
    async def apply(self, srv, desired: list[ClientMaterial], remove: list[str]) -> None
    async def read_traffic(self, srv) -> dict[str, Counter]           # client_id -> (rx, tx, session)
    def render(self, material, srv_params) -> Rendered                # vpn_key, native, qr_svg
```

**Подготовка** выполняется один раз при подключении сервера. Если нужна правка конфига контейнера и его перезапуск, администратор подтверждает это заранее: подключения на несколько секунд оборвутся.

| Контейнер | Подготовка | Создание | Блокировка и разблокировка | Удаление | Трафик |
|---|---|---|---|---|---|
| AWG, WireGuard | не нужна | ключи генерирует панель, IP берётся свободный из подсети; peer добавляется в `wg0.conf`, затем `wg syncconf wg0 <(wg-quick strip …)` | peer убирается из конфига или возвращается, затем `syncconf`; ключи и IP остаются в БД | peer убирается, материал удаляется | `wg show wg0 dump` |
| Xray (VLESS/Reality, SS over Xray) | в `server.json` добавляются `api`, `stats`, `policy` и inbound для API; `email` клиента = id конфига | `xray api adu` и запись в файл | `xray api rmu`/`adu` и файл; запасной путь — правка файла и `docker restart` | как блокировка | `xray api statsquery` |
| OpenVPN (plain, Cloak, SS) | в `server.conf` добавляются `client-config-dir` и `management` | ключ и CSR генерирует панель, затем `easyrsa import-req` и `sign-req` | `ccd/<CN>` со строкой `disable` и kill сессии через management | `easyrsa revoke` и `gen-crl` | `openvpn-status.log`, счётчики сессионные |
| IKEv2 | не нужна | клиентский сертификат через `certutil`, p12 хранится в БД | CRL перевыпускается с серийным номером сертификата или без него | revoke | `ipsec trafficstatus`, сессионные |
| SOCKS5 (3proxy) | контейнер переводится на список `users` | строка `login:CL:pass` | строка убирается или возвращается, затем reload | строка убирается | JSON-лог 3proxy, поле `bytes` |
| MTProxy | несколько секретов (`-S` повторяется) | свой секрет на конфиг | секрет убирается или возвращается, затем рестарт | секрет убирается | нет, в интерфейсе «н/д» |
| Telemt | секция users | свой секрет на конфиг | как у MTProxy | как у MTProxy | статистика Telemt по пользователям, если она есть; если нет, «н/д», как у MTProxy |
| SFTP, Tor-сайт, TProxy | — | пользователям не выдаются, видны только в карточке сервера | — | — | — |

Скрипты и пути берутся из `client/server_scripts/` и из существующих configurators, чтобы поведение совпадало с Qt-клиентом.

**Формат `vpn://`.** Это `qCompress(JSON)` в base64url: 4 байта длины исходных данных (big-endian), затем данные zlib. Совместимость с Qt-клиентом проверяется тестом: ключ, сгенерированный панелью, разбирается кодом клиента или его эталонной выборкой.

## 7. REST API

Все пути начинаются с `/api`. Ошибки возвращаются в формате `{code, message}`, где `code` — стабильный машинный код. Контрактом служит OpenAPI-схема, которую генерирует FastAPI.

### Авторизация

- `POST /auth/login {login, password, role}` возвращает непрозрачный токен.
- Веб получает токен в cookie `HttpOnly; Secure; SameSite=Strict` и отправляет CSRF-заголовок в запросах с изменениями. Qt-клиент передаёт токен в `Authorization: Bearer`.
- Время жизни токена: 12 часов у администратора, 30 дней у пользователя. Срок продлевается при использовании.
- `POST /auth/logout`.
- `POST /auth/invite/check {key}` и `POST /auth/invite/redeem {key, login, password}`.
- Ограничения частоты:
  - вход: 5 попыток в минуту на логин и 20 в минуту на IP;
  - ключи приглашения: 10 попыток в час на IP.
- Пароль:
  - хешируется argon2id;
  - длина не меньше 12 символов;
  - оценка zxcvbn не ниже 3.

  Политика одна для регистрации и смены пароля.
- Первый администратор создаётся командой `panel create-admin` внутри контейнера.

### Администратор: `/admin`

### Прочее

- `GET /jobs/{id}` возвращает статус асинхронной задачи.
- Создание конфига выполняется синхронно с таймаутом 30 секунд: ответ приходит только после применения на сервере. Если сервер недоступен, возвращается `503 server_unavailable`, и в БД ничего не записывается.
- Заблокированный пользователь или пользователь с истёкшим сроком получает `403 user_blocked` или `403 user_expired` на создание и выдачу конфигов.

## 8. Задачи, планировщик, отказоустойчивость

### Очередь задач

- Задачи хранятся в таблице `jobs` и забираются через `SELECT … FOR UPDATE SKIP LOCKED`.
- Воркер работает в процессе backend.
- На один сервер одновременно выполняется только одна задача (`pg_advisory_lock(server_id)`).
- Одинаковые задачи `reconcile(server)` в очереди объединяются.
- После ошибки задача повторяется с задержкой 1, 2, 4 … минуты, но не больше 30. Причина ошибки пишется в `servers.last_error`.

### Периодические задачи (APScheduler)

- `expire_users`, раз в минуту: пользователям с наступившим сроком ставится `blocked_by = 'expiry'` и сверка затронутых серверов.
- `collect_traffic`, раз в 5 минут на каждый сервер.
- `reconcile_all`, раз в 15 минут на каждый сервер. Это страховка от ручных правок и потерянных задач.
- `cleanup`, раз в сутки: удаляются просроченные сессии и задачи старше 30 дней.

### SSH

- Используется пул соединений asyncssh.
- Ключ хоста запоминается при первом подключении (TOFU).
- Если ключ хоста сменился, задачи сервера останавливаются до подтверждения администратором.

### Сбои

- Если панель упала, VPN продолжает работать.
- После рестарта `expire_users` и `reconcile_all` догоняют пропущенное.

### Безопасность данных

- Поля `*_enc` шифруются AES-256-GCM. Мастер-ключ задаётся в env `PANEL_MASTER_KEY`.
- Каждый день делается `pg_dump` в отдельный том.
- В README есть предупреждение: без `PANEL_MASTER_KEY` бэкап не восстановить.

### Аудит

Каждое изменяющее действие администратора, пользователя или системы пишется в `audit_log`.

## 9. Веб-интерфейс (`panel/web`)

Стек:

- React, TypeScript, Vite;
- React Router, TanStack Query;
- Mantine;
- Recharts;
- react-i18next с языками `ru` (по умолчанию) и `en`.

Типы API генерируются из OpenAPI (`openapi-typescript`).

### Пользователь

- `/login`: логин и пароль, под формой кнопка «Ввести ключ для авторизации».
- `/invite`: пользователь вводит ключ, затем логин, пароль и повтор пароля. Индикатор показывает, выполняются ли требования к паролю.
- `/`: дашборд.
  - В шапке срок доступа и «конфигов N из M».
  - Карточки серверов с протоколами и кнопкой «Создать конфиг».
  - Таблица конфигов: сервер, протокол, имя, статус, трафик.
  - Действия: «Показать», «Блокировать» или «Разблокировать», «Удалить».
  - «Показать» открывает окно: ключ `vpn://`, нативный конфиг, QR-код, копирование и скачивание файла.
- `/account`: смена пароля.

### Администратор (`/admin`)

- Пользователи:
  - список с фильтрами;
  - создание пользователя, после которого ключ приглашения показывается один раз;
  - карточка пользователя: срок, лимит, блокировка, удаление, перевыпуск ключа, конфиги, трафик (итог, по серверам, график по дням).
- Серверы: добавление, статус сверки, контейнеры, установка, подтверждение ключа хоста.
- Конфиги без владельца: привязка к пользователю.
- Журнал действий.

Удаление и блокировка требуют подтверждения. Задачи отображают прогресс.

## 12. Тестирование

- **Модульные тесты (pytest).**
  - Правила из §5: лимит, блокировки, срок, дельты трафика, ключи приглашения, политика паролей.
  - Время подменяется через внедряемые часы.
- **API.** pytest, httpx, PostgreSQL в testcontainers. Проверяются права ролей, коды ошибок и гонка лимита при параллельных запросах.
- **Драйверы.**
  - Интеграционные тесты на контейнерах, собранных из `client/server_scripts/*/Dockerfile`, внутри контейнера-«хоста» с SSH и Docker (docker-in-docker).
  - Для каждого протокола проверяется цепочка: создать → работает → заблокировать → не работает → разблокировать → работает → удалить.
  - «Работает» проверяется клиентом внутри тестовой сети.
- **Совместимость `vpn://`.** Ключ, сгенерированный панелью, разбирается эталонной логикой Qt-клиента.
- **Веб.** Playwright на основные сценарии:
  - регистрация по ключу;
  - вход;
  - создание и выдача конфига;
  - блокировка;
  - смена пароля;
  - создание пользователя администратором.
- **Qt.** Сборка под затронутые платформы (unit-тестов у приложения нет) и ручная проверка сценариев против тестовой панели.

## 13. Риски

- **IKEv2.** Не проверено, надёжно ли libreswan работает с перевыпуском CRL. Если нет, блокировка будет означать удаление, а разблокировка — перевыпуск конфига. Пользователь получит новый конфиг.
- **Xray.** Если версия Xray в контейнере не поддерживает `api adu/rmu`, блокировка перезапускает контейнер. Все клиенты этого сервера переподключатся.
- **MTProxy.** Трафик по пользователям недоступен.
- **Импорт.** У импортированных конфигов нет приватной части. Их можно блокировать и удалять, но повторно выдать нельзя. Для выдачи нужен перевыпуск.
- **Секреты.** Панель хранит SSH-доступы ко всем серверам. Её компрометация означает компрометацию всех серверов. Меры: шифрование секретов в БД, TLS, ограничение частоты входа, аудит, отдельный VPS.
